Which message goes where

The split is deliberate. Bluetooth frames are chunked and reassembled by hand, so only small self-contained payloads are trusted to it — at a venue you exchange what was bought, not what the item is.

travelsOverBluetooth is true for setStatus and nothing else. Item names, costs, assignees and joins go over the relay exclusively. The want still carries the gapless prefix of the whole log: holding every change up to n includes every status flip up to n, while a prefix over the subset was always empty, since a device's first change is its memberJoined.

Keys and identifiers

Everything derives from one 32-byte session key, which travels only in the join link. The link is circles-app://buys-join?v=1&e=<event>&k=<base64url key>. 

// 32-byte session key, generated once by whoever starts the room
roomID        = HMAC-SHA256(sessionKey, "circles-buys/v1/topic")[0..16]   → 32 hex chars
contentKey    = HKDF-SHA256(sessionKey, info: "circles-buys/v1/ops",        len 32)
relayAuthKey  = HKDF-SHA256(sessionKey, info: "circles-buys/v1/relay-auth", len 32)
handshakeKey  = HKDF-SHA256(sessionKey, info: "circles-buys/v1/ble-handshake", len 32)

deviceID      = 4 random bytes                                            → 8 hex chars
nonce         = 12 random bytes                                           → AES-GCM
aad           = roomID(16) ‖ deviceID(4) ‖ u64be(seq)                     → 28 bytes
blob          = 53 42 32 00 ‖ nonce ‖ AES-256-GCM(contentKey, nonce, aad, payloadJSON) ‖ gcmTag(16)

recordTag     = HMAC-SHA256(relayAuthKey, deviceID ‖ 0x00 ‖ u64be(seq) ‖ blob)[0..16]
helloTag      = HMAC-SHA256(relayAuthKey, "hello" ‖ 0x00 ‖ deviceID ‖ 0x00 ‖ u64be(ts))[0..16]
helloInput     = "hello"  ‖ 0x00 ‖ deviceID ‖ 0x00 ‖ u64be(ts)
attestInput    = "attest" ‖ 0x00 ‖ roomID   ‖ 0x00 ‖ helloInput                → 63 bytes
clientDataHash = SHA-256(attestInput)                                          → App Attest clientDataHash, Play requestHash
sessionTag    = HMAC-SHA256(sessionKey,   "ble" ‖ u64be(window))[0..2]    window = ⌊unix/900⌋
seq counts one device's own changes, with no gaps.

(deviceID, seq) is the primary key everywhere — in the relay's table and in client dedup — and both sync paths ask by gapless prefix, so a device's numbering must run 1, 2, 3… A reused number is silently dropped by the relay as a duplicate, which is why a client raises its counter past any of its own records the relay hands back. Ordering across devices is a separate Lamport clock carried in the payload as l, advanced past every record ingested; a payload without it orders by seq. Blobs from before random nonces used deviceID ‖ u64be(seq) as the nonce and carry no marker; clients still open them but never write one.

Relay · authenticated upgrade and WebSocket JSON

The upgrade carries X-Circles-Hello: base64url of the complete hello JSON in UTF-8, at most 16 KiB after decoding. Attestation is verified before accessing a room, and room/device tags are verified before accepting a WebSocket. Refused upgrades return an HTTP error with the JSON err shape; unauthenticated requests never occupy socket slots. The client sends no hello frame after upgrade; an accepted connection immediately receives held and ops.

One text frame per message, at most 4096 bytes, to wss://<host>/r/<32 hex roomID>. Binary frames are refused. The relay moves records and never inspects them: it cannot decrypt a blob, and since it holds relayAuthKey only to rate-bind a room, clients verify recordTag themselves on ingest.

A tagged union: t is "appattest" or "playintegrity", and nothing else — there is no default branch and no unattested fallback. Always required on a deployed relay, with no variable to enable it and none that can turn it off; a local run reached over loopback can relax it to optional or off through .dev.vars. Anything that fails to verify refuses the upgrade with HTTP 401.
pobject?Push registration, stored only after the tag verifies: pl is "apns" or "fcm", tk is the platform token (≤512 chars of [A-Za-z0-9_:.-]), e is "sandbox" or "production" and defaults to sandbox. One token per device, replaced on every hello. Anything malformed refuses the upgrade with HTTP 400.

A device that registered a token and is not currently connected gets a content-free wake-up when another member writes: {"aps":{"content-available":1}} over APNs, or a data-only high-priority message over FCM. The relay never composes user-visible content — it cannot, since it holds no key. The woken client reconnects, catches up, and renders locally. Wake-ups are coalesced to one per device per 10 seconds, and a token the platform reports as gone is dropped.

Attestation says the peer is a real build on real hardware — nothing more.

The room key already proves physical presence: whoever holds it finished the Bluetooth handshake. at proves something orthogonal, that the socket belongs to an unmodified CiRCLES on a device its vendor still vouches for. Neither says a record is true, so records stay the clients' to validate and the relay stays a pipe.

Both mechanisms bind to the same clientDataHash, so one challenge construction covers two carriers. It is checked once per hello, never per record — a signature check and a counter write on every record would make the relay a bottleneck and buy nothing the hello has not already established. 

Apple   "at": { "t": "appattest", "k": keyId, "o": attestationObject }   // first hello of an install
        "at": { "t": "appattest", "k": keyId, "s": assertion }          // every hello after
Google  "at": { "t": "playintegrity", "tk": token }                     // standard request, every hello

Apple's path enrolls once — chain to Apple's App Attest root, nonce, key id, app id, zero counter, environment — and then verifies a cheap assertion against the stored key in a separate identity object, refusing any counter that fails to advance. Every re-enrollment of the same key is refused, so a replayed enrollment cannot reset it. Google's path has no durable key: every hello carries a fresh token that the relay hands to playintegrity.googleapis.com to decode, then checks the package, the request hash, the token age, PLAY_RECOGNIZED, and the device verdict against PLAY_MIN_VERDICT.

Absent evidence is an admission error on a deployed relay: App Attest reports unsupported in the Simulator, on Mac — Catalyst included — and in app extensions, and Play Integrity returns nothing useful without Google Play services. With a local relay relaxed to optional such a device still syncs; against a deployed one it cannot, since attestation there is not optional — and because that refusal can never succeed, a client that sent no evidence and was refused with HTTP 401 stops reconnecting instead of retrying for the life of the room.

held

relay → client · once, right after a verified hello 
{
  "t": "held",
  "n": 41                       // highest gapless seq the relay holds for the hello device
}

Sent before the ops reply to the hello, so a client uploads only its own records above n instead of its whole history on every reconnect. A client that sees the hello's ops reply without a held ahead of it is talking to an older relay and falls back to uploading everything it authored.

Bluetooth · GATT

Every device runs both roles at once: a peripheral advertising the service, and a central scanning for it. Which side writes depends on who discovered whom, so the same peer pair may exchange a message down both paths — reassembly is kept separate per role for exactly that reason.

Advertisement — 6 bytes

Android puts these bytes in the scan response as service data; iOS cannot advertise service data, so it hex-encodes the same six bytes into the local name (12 characters). Both platforms read either field. A peer carrying the wrong room tag is rejected before connecting and backed off for 60 seconds; a peer carrying no bytes at all still gets a chance, because a backgrounded iOS app cannot advertise a name.

Handshake — challenge, response, confirm

The central writes a challenge to the peer's inbox once notifications are enabled. The peripheral answers any challenge with its own nonce and a MAC over both; the central checks it and writes a confirm under a different label, so neither MAC can be reflected back as the other. Only then is either side verified, and until it is, nothing else from that peer is accepted. The advertisement's tag is not proof of anything — every scanner in range can read it — and only filters discovery. A central that has not verified a peer within 10 seconds drops it and backs it off for 60; an Android peripheral drops a central that never confirms on the same deadline. 

challenge  = 0x03 ‖ nonceC(8)                                              central → peripheral, 9 B
response   = 0x04 ‖ nonceP(8) ‖ HMAC(handshakeKey, "resp" ‖ nonceC ‖ nonceP)[0..8]   peripheral → central, 17 B
confirm    = 0x05 ‖ HMAC(handshakeKey, "conf" ‖ nonceC ‖ nonceP)[0..8]              central → peripheral, 9 B

Every frame fits the 20 bytes a link at the default MTU carries, and is told apart from a chunk frame (0x01) by first byte and exact length. Test vector: session key 00 01 … 1f, nonceC 01 … 08, nonceP 11 … 18 give response 04111213141516171812f9003d9145f14c and confirm 05cff3acad54e390af.

Chunk header — 4 bytes + body

Wire frames are cut to whatever the link negotiated: body size is min(160, MTU − 3 − 4), so a connection stuck at the 23-byte default MTU sends 16-byte bodies rather than silently truncating a 160-byte one. A message needing more than 255 chunks cannot be described by this header and is not sent.

Three header bytes, then count bodies of the declared type. Records are packed so that each frame fits inside a single chunk wherever possible; a record too large for one chunk still gets its own frame and is split by the layer above rather than dropped.

The receiver replies, to the sender alone, with every Bluetooth-eligible change whose seq exceeds the value given for its device — and everything for a device the frame never mentions. Only the side that connected sends the first want on a link, and skips it when the advertised digest matches its own; the other side sends one back, once per link, only if the two vectors differ.

A k outside 0–6 is stored, counted in the version vector, and folded as a no-op on both platforms; a v outside 0–2 is kept as it arrived. Either one being coerced or dropped on one platform and kept on the other is how two devices holding the same log end up showing different totals.
