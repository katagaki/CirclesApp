Which message goes where

The split is deliberate. Bluetooth frames are chunked and reassembled by hand, so only small self-contained payloads are trusted to it — at a venue you exchange what was bought, not what the item is.

travelsOverBluetooth is true for setStatus and nothing else. Item names, costs, assignees and joins go over the relay exclusively, and a receiver drops any other kind that arrives over Bluetooth — that is how a member in range would otherwise announce a signing key of their own for a device whose memberJoined has not reached us yet. The want still carries the gapless prefix of the whole log: holding every change up to n includes every status flip up to n, while a prefix over the subset was always empty, since a device's first change is its memberJoined.

Keys and identifiers

Everything derives from one 32-byte session key, which travels only in the join link or sealed in a rekey. The link is circles-app://buys-join?v=1&e=<event>&k=<base64url key>&o=<owner device>. o is the 8 hex deviceID of the member who started the room; links without it still join, but such a member never follows a re-key. A room's key never changes: replacing it means moving to a new room, as described under Re-keying a room.

seq counts one device's own changes, with no gaps.

(deviceID, seq) is the primary key everywhere — in the relay's table and in client dedup — and both sync paths ask by gapless prefix, so a device's numbering must run 1, 2, 3… A reused number is silently dropped by the relay as a duplicate, which is why a client raises its counter past any of its own records the relay hands back. Ordering across devices is a separate Lamport clock carried in the payload as l, advanced past every record ingested; a payload without it orders by seq. Blobs from before random nonces used deviceID ‖ u64be(seq) as the nonce and carry no marker; clients still open them but never write one.

Relay · authenticated upgrade and WebSocket JSON

The upgrade carries X-Circles-Hello, base64url of the complete hello JSON in UTF-8, and X-Circles-Attest, base64url of the evidence JSON in UTF-8, each at most 16 KiB after decoding. The evidence signs the exact hello bytes, so no field of the hello can be changed without invalidating it. Attestation is verified before accessing a room — after a per-IP limit of 30 checks a minute, which answers HTTP 429 — and room/device tags are verified before accepting a WebSocket. Refused upgrades return an HTTP error with the JSON err shape; unauthenticated requests never occupy socket slots. The client sends no hello frame after upgrade; an accepted connection immediately receives held and ops.

One text frame per message, at most 4096 bytes, to wss://<host>/r/<32 hex roomID>. Binary frames are refused. The relay moves records and never inspects them: it cannot decrypt a blob, and since it holds relayAuthKey to bind a room, clients verify recordTag themselves on ingest. That key is shared by every member and the relay, so a valid recordTag proves a record came from someone in the room, not which device wrote it. Which device wrote it is the per-device signature inside the blob, checked by clients alone — see Per-device signatures.

A device that registered a token and is not currently connected gets a content-free wake-up when another member writes: {"aps":{"content-available":1}} over APNs, or a data-only high-priority message over FCM. The relay never composes user-visible content — it cannot, since it holds no key. The woken client reconnects, catches up, and renders locally. Wake-ups are coalesced to one per device per 10 seconds, and a token the platform reports as gone is dropped.

Attestation says the peer is a real build on real hardware — nothing more.

The room key already proves physical presence: whoever holds it finished the Bluetooth handshake. The evidence proves something orthogonal, that the socket belongs to an unmodified CiRCLES on a device its vendor still vouches for. Neither says a record is true, so records stay the clients' to validate and the relay stays a pipe.

Both mechanisms bind to the same clientDataHash, so one challenge construction covers two carriers. It is checked once per hello, never per record — a signature check and a counter write on every record would make the relay a bottleneck and buy nothing the hello has not already established. 

Apple   { "t": "appattest", "k": keyId, "o": attestationObject }   // first hello of an install
        { "t": "appattest", "k": keyId, "s": assertion }          // every hello after
Google  { "t": "playintegrity", "tk": token }                     // standard request, every hello

Apple's path enrolls once — chain to Apple's App Attest root, nonce, key id, app id, zero counter, environment — and then verifies a cheap assertion against the stored key in a separate identity object, refusing any counter that fails to advance. Every re-enrollment of the same key is refused, so a replayed enrollment cannot reset it. Google's path has no durable key: every hello carries a fresh token that the relay hands to playintegrity.googleapis.com to decode — only once it is made of JWT characters, so garbage never spends the decode quota — then checks the package, the request hash, the token age, PLAY_RECOGNIZED, and the device verdict against PLAY_MIN_VERDICT. Google does not protect a standard request against replay, so the request hash would let a captured hello and token be presented again within the skew window; the room's record of admitted hellos refuses that second use.

Absent evidence is an admission error on a deployed relay: App Attest reports unsupported in the Simulator, on Mac — Catalyst included — and in app extensions, and Play Integrity returns nothing useful without Google Play services. With a local relay relaxed to optional such a device still syncs; against a deployed one it cannot, since attestation there is not optional — and because that refusal can never succeed, a client that sent no evidence and was refused with HTTP 403 stops reconnecting instead of retrying for the life of the room.

Advertisement — 6 bytes

Android puts these bytes in the scan response as service data; iOS cannot advertise service data, so it hex-encodes the same six bytes into the local name (12 characters). Both platforms read either field. Handshake — challenge, response, confirm

The central writes a challenge to the peer's inbox once notifications are enabled. The peripheral answers any challenge with its own nonce and a MAC over both; the central checks it and writes a confirm under a different label, so neither MAC can be reflected back as the other. Only then is either side verified, and until it is, nothing else from that peer is accepted. The advertisement's tag is not proof of anything — every scanner in range can read it — and only filters discovery. A central that has not verified a peer within 10 seconds drops it and backs it off for 60; an Android peripheral drops a central that never confirms on the same deadline. 

challenge  = 0x03 ‖ nonceC(8)                                              central → peripheral, 9 B
response   = 0x04 ‖ nonceP(8) ‖ HMAC(handshakeKey, "resp" ‖ nonceC ‖ nonceP)[0..8]   peripheral → central, 17 B
confirm    = 0x05 ‖ HMAC(handshakeKey, "conf" ‖ nonceC ‖ nonceP)[0..8]              central → peripheral, 9 B

Every frame fits the 20 bytes a link at the default MTU carries, and is told apart from a chunk frame (0x01) by first byte and exact length. Test vector: session key 00 01 … 1f, nonceC 01 … 08, nonceP 11 … 18 give response 04111213141516171812f9003d9145f14c and confirm 05cff3acad54e390af.

Chunk header — 4 bytes + body

Wire frames are cut to whatever the link negotiated: body size is min(160, MTU − 3 − 4), so a connection stuck at the 23-byte default MTU sends 16-byte bodies rather than silently truncating a 160-byte one. A message needing more than 255 chunks cannot be described by this header and is not sent.

Per-device signatures

The room key proves a record came from a member, not which member. Each device therefore signs every record it writes with its own Ed25519 key, and announces that key once, in its memberJoined. A member holding the room key can still read and write as themselves, but no longer as anyone else — over Bluetooth or through the relay, and the relay cannot do it either. 

fields = i64be(a) ‖ i64be(k) ‖ str(i) ‖ i64be(c)
       ‖ opt(t, str) ‖ opt(v, i64be) ‖ opt(s, str) ‖ opt(l, i64be) ‖ opt(p, str)

str(x)        = u32be(len(utf8(x))) ‖ utf8(x)
opt(x, enc)   = 0x00                      absent
              | 0x01 ‖ enc(x)             present

The signature covers the payload's fields in this fixed layout, not the JSON and not the blob. A peer answering a want re-seals other devices' changes under a fresh nonce and re-encodes their JSON, so neither the ciphertext nor the plaintext bytes survive forwarding; the fields, and with them the signature, do. Every field but g is covered, including p, so memberJoined is self-signed. A field added later must extend this layout under a new signInput label. The signature travels inside the sealed payload, so neither transport's framing changes and the relay never sees it.

A device's state is decided by its first memberJoined, by seq, which is always its seq 1. Clients open each incoming batch in (device, seq) order and one batch at a time, so a device's join is in the log before anything it signed is checked. A record from a device whose join has not arrived is dropped rather than kept: keeping it would let whichever copy of a (device, seq) arrived first win, forged or not. Since the version vector never claimed it, it is offered again on the next want or relay hello. Dropped records are verified again from scratch each time they arrive; nothing is cached as rejected.

Rollout: a mixed room keeps working, and gets stricter as it upgrades.

Nothing on the wire changes shape: p and g are new optional JSON keys inside the blob, and both apps' decoders ignore keys they do not know. Older builds read signed records as they always read records, and the relay needs no change.

A device that joined from an older build has a memberJoined without p, and stays unsigned in that room for its lifetime, even after the app updates — its records are trusted exactly as much as before. A device that joined from a signing build is protected from its first record on, in every signing client. An older build forwarding a signed flip over Bluetooth re-encodes it without g; signing clients drop that copy and take the author's own, from the relay or from a peer that kept the signature.

What signatures do not cover.

Older builds verify nothing, so they can still be shown forged records for any device. Records of an unsigned device can still be forged by any member. The key is pinned on first sight: a device's memberJoined reaches clients only through the relay, which accepts records for a device only from the socket holding that device's x, so pinning a false key takes a member colluding with the relay before the real device's join lands. The actor a and the nickname remain what the device says they are; the signature binds them to a device, not to a circle.ms account.

Why the sender check holds.

Every member holds the old key, so a removed member can seal a rekey to anyone. The relay binds each socket to one registered device and refuses records claiming another, so a rekey written as the owner's device can only come from the owner — or from the relay itself, which holds no content key and so cannot produce a record that opens. Bluetooth has no such binding, which is why a receiver drops every kind but setStatus it opens from a peer.

What re-keying does not do.

The old room stays readable to anyone with the old key until it expires, history included; a removed member keeps whatever they already saw. A member whose build never wrote a memberKey, or who joined from a link without o, is left behind and has to be given the new link. Changes written to the old room after the owner left are not carried. Old clients ignore kinds 8 and 9 as unknown, so nothing about this changes the wire for them or for the relay.

Roles are advisory.

A guest is a member whose app writes only setStatus, memberJoined and memberKey. Nothing enforces that: a guest holds the session key, so a modified client can write any kind the relay accepts, and the relay cannot tell kinds apart. The only role the log honours is the owner's, and only for following a rekey; removing someone is re-keying without them.
