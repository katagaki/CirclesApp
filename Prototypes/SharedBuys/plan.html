How it works

Three situations, handled the same way

Changes normally go out over the internet, because that reaches everyone wherever they are standing. Phone-to-phone takes over when the network is dead — or merely bad. Neither is visible to the user.

Normal

One connection each, held open. Changes are pushed out the instant they happen — never fetched on a timer — and reach everyone at once.

Bad signal

Rather than hammering away at reconnecting, phones near each other pass changes directly over Bluetooth until the network settles. This is what keeps the bill at zero.

Nothing at all

Changes are kept on the phone and sent the moment either path returns. Nothing is ever lost, and nothing needs retrying by hand.

The thing that actually costs money

Connecting, not talking

On the free plan, sending a change out to the group costs nothing at all, and the keepalive is free too. What gets counted is opening a connection — so a flaky hall network that drops the socket every few minutes is the one thing that could run the budget dry.

  • One connection per person, held open for the whole session
  • Reconnects backed off and staggered, never retried in a tight loop
  • No reconnecting at all while phones nearby are already passing changes along
  • Rapid taps grouped into one send instead of eight
  • Photos never go over Bluetooth — only over Wi-Fi, and only when opened
Measured in the prototype

Only what's missing crosses a radio

The relay

One small Worker, already built

The relay exists and is deployed — it lives in its own repository, separate from both apps. No servers to run, no database to manage, no monthly bill. What remains is the app's side of the conversation.

What it's built on

  • Cloudflare Workers, free plan
  • Durable Objects — one per list
  • Hibernation, which is required, not optional
  • No storage service, no queue, nothing else

What it does

  • Keeps a room's changes for 48 hours, then deletes them
  • Sends each new change straight to everyone else
  • Catches up anyone who reconnects
  • Sends the lock-screen updates too

Where it already is

  • Beta and live, deployed by tagging
  • Debug builds talk to beta, releases to live
  • Built-in analytics, alerting well under the daily cap
  • Its own repository and its own credentials

What breaks if it's down

  • Phones fall back to talking directly
  • Changes queue up and go later
  • No error message — there is nothing for anyone to do
  • Nothing is lost
Security

The relay can't read the list

✓Everything is locked with a key that only exists in the QR code and on members' phones. The relay stores sealed bytes it cannot open.
✓Nothing secret ships inside the app, so there is no key to leak or rotate.
✓Each message is signed with a second key, so strangers can't write into a room even if they somehow found it. That signature is a spam gate — proof of membership is that the contents unlock at all, which the relay can never do.
✓Room names are 128-bit and unguessable.
✓No names, no account numbers, no item text, and no message logging — nothing stored identifies a person.
✓Hard caps per room: message size, message rate, number of people, number of changes, and a 48-hour life.

Joining a list

The QR is the whole handshake

Scanning is not a request to a server that then lets you in. The code itself contains everything needed, so two phones that have never been online can still end up on the same list.

Nothing above touches a server. Two phones with no signal at all can pair and start sharing, and the relay only ever learns a room name it cannot work backwards from.

Security

Locked before it leaves the phone

Nothing trusts the connection it travels over. Every change is sealed on the device that made it, and the identical sealed bytes go out over Bluetooth and over the internet alike.

One key, four jobs

Only the first of the four ever unlocks anything, and it never leaves the members' phones.

Choices worth knowing

Three that aren't obvious

Bluetooth's own encryption is switched off on purpose

Turning it on means a system pairing prompt — the exact friction the QR removes — and it varies by handset, and it wouldn't stop a phone that joined legitimately. The list is already locked, so the link doesn't need to be.

The lock is picked by its number, not by chance

Everyone shares one key, so two phones must never accidentally lock two changes the same way — that breaks this kind of encryption wide open. Each change is locked using its own identity, which is unique by construction, so a collision can't happen at all.

The signal tag changes every 15 minutes

Otherwise a fixed Bluetooth tag would be a beacon anyone could follow around the hall. It rolls on a clock all members share.

Sealing one change

Locked once, then never touched again

The same bytes go either way, so neither path has to be trusted — and if a change opens on the far end, whoever sent it had the key. That is the only proof of membership anyone needs.

Why two phones can't clash

Implementation

What gets built

Who you are

The circle.ms account already in the app. No new sign-up, no new user list — the same identity works on both platforms.

What a change is

A small note — added, claimed, bought, cancelled — with an order number. Phones swap notes and replay them in the same order, so they always land on the same list.

Where it's kept

Three new tables in the Buys database that's already there. Private Buys are untouched; an item can be promoted into the shared list.

Keeping both apps honest

One shared set of test cases — a list of changes and the exact list they must produce — checked into both repos. iOS and Android must agree byte for byte.

Build order

Five steps, each shippable

Steps 1 and 2 are built and working across both platforms against a local relay. Step 3 is written but needs real hardware. The list still lives behind a debug harness, not in the app's own UI.

DONE STEP 1

The list itself

Changes, replay, and the UI, behind a flag. No radios yet. This is what the prototype already is.

DONE STEP 2

Joining, and the app's side of the relay

The server is done, so this is key handling and the connection. It makes the feature work end to end on both platforms before any radio work starts.

WRITTEN STEP 3

Phone to phone

Bluetooth, same platform first, then across. Written on both platforms, but a simulator has no radio — this one needs two real handsets to confirm.

HALF STEP 4

Live Activity

Running on iOS — lock screen and Dynamic Island, updating as the list changes. Android's notification and the push path are still to do.

TO DO STEP 5

Photos

Item pictures, fetched only when someone opens them.

Known problems

Six, and what we're doing about each

CLOSED

A sleeping iPhone can't be seen by Android

When the app isn't open, iOS hides its Bluetooth signature somewhere only other iPhones can read.

Decision

Android always does the broadcasting — it's already running a foreground service for its notification. A sleeping iPhone listens and reaches out. Every combination is covered; the only cost is that a Bluetooth-only catch-up can take tens of seconds.

MITIGATED

Tens of thousands of phones in one hall

Spotting a friend's phone is cheap. Actually connecting, in that much radio noise, can take seconds or fail.

Decision

Mostly don't connect. A phone broadcasting the same fingerprint as ours is left alone entirely. Beyond that: two connection attempts at a time, one retry per phone per minute, and never make the screen wait for one.

NARROWED

Anyone who photographs the QR is in

Instant joining is the whole point, so an approval prompt isn't the answer.

Decision

Make joins visible — everyone sees 「Aoiが参加しました」— and make removal real: taking someone out issues a brand-new key to everyone else. The removed phone is left holding something that no longer opens anything. Marking them as removed wouldn't have done that.

GUARDED

If the free allowance runs out, it runs out for everyone

There's one relay and no second one. The failure would land on the three days a year that matter.

Decision

Guard the input, not the output: reconnect discipline is the mitigation, since that's the only thing that can realistically drain it. Alert at half the daily cap. If it ever happens, phones fall back to talking directly — line-of-sight only, but still working, and still silent.

BOUNDED

Clocks drift, and the Bluetooth tag depends on one

The tag rolls every 15 minutes so it can't be used to follow someone. Two phones with very different clocks would compute different tags.

Decision

Each phone accepts the tag either side of the current one, so a clock up to about 15 minutes out still matches. Both platforms set their clocks from the network anyway. This affects finding each other only — the order of changes never depends on the time.

DESIGNED

iPad's docked panel is narrow

On iPad the panel sits in a 360pt sidebar, which is where the new rows are tightest.

Decision

The sharing row drops to faces and a count. Item names truncate; price and face stay put. The QR opens as a full sheet rather than a popover — an iPad is held further away from the phone scanning it, so the code has to be physically bigger.

STILL OPEN

Does the Worker's own outgoing push count against the allowance?

Sending lock-screen updates means the Worker calling Apple and Google. Those are outgoing calls rather than incoming ones, which suggests they're not counted — but it needs confirming before that step, because it changes the budget if they are.
