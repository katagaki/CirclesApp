# Shared Buys — implementation plan

A shared, realtime Buys list for CiRCLES (iOS) and CirclesGo (Android), designed for a
crowded convention hall with unreliable Wi-Fi, on a zero-cost operating budget.

## 1. Constraints this design is shaped by

| Constraint | Consequence |
| --- | --- |
| Free to operate | No paid services. One Cloudflare Workers free-tier relay, and nothing else. The free tier's request accounting shapes the design — see §5b. |
| Cross platform | No MultipeerConnectivity, no Nearby Connections, no CloudKit sharing. BLE GATT + WebSocket are the only two transports both platforms speak. |
| Spotty venue internet | The relay is the default path, but nothing may *depend* on it. Bluetooth carries the group when the network is dead, and absorbs reconnect churn when it is merely bad. |
| Minimal power | The sync engine's job is to *not* turn radios on. See §9. |
| Not always-on | A session is explicitly started, is bound to a Live Activity, and dies with it. |
| Realtime assignment + status | Every change is an op in a shared log; ops stream both ways over whichever transport is up. |

## 2. Identity

The logged-in circle.ms user already gives a stable, cross-platform identity:
`UserInfo.Response.pid` (`RADiUS/Catalog/UserInfo.swift`) plus `nickname`. That is the
actor on every op and the assignee on every item. No new account system, no server-side
user table.

Each *install* also gets a random 4-byte `deviceID`, used only to make op IDs unique and
to key the version vector. One user on two devices is legal and converges.

## 3. Data model: an op log, not a synced document

State is derived, never transmitted. Each mutation is an immutable op:

```
Op {
  lamport:  varint      // Lamport clock, per device
  device:   4 bytes     // deviceID
  actor:    varint      // circle.ms pid
  kind:     u8          // addItem | setStatus | setAssignee | setCost | removeItem | memberJoined | revoke
  itemID:   8 bytes     // ULID prefix, generated by the creating device
  circleID: varint
  payload:  text? int?
}
```

Op identity is `(device, lamport)`. Encoded as CBOR an op is ~45 bytes; the prototype's
JSON encoding measured 113–130 B per op, so budget ~50 B in production.

**Fold**: sort by `(lamport, device)`, apply in order. Every field is last-writer-wins
under that total order, which is deterministic on every replica, so all devices reach the
same list without any coordination. `addItem` is add-only, `removeItem` is a tombstone.
This is implemented in `SessionFold.items(from:)` in the prototype and is the *only* piece
of logic that must be byte-identical between Swift and Kotlin — ship golden test vectors
(a JSON fixture of ops → expected state) in both repos.

**Version vector**: `{deviceID: maxLamport}`. `missing(from:)` gives exactly the ops a peer
lacks. A 2-byte **state digest** (FNV-1a over the sorted vector) is what gets advertised
over BLE, so peers can decide "we are identical, do nothing" without connecting.

## 4. Pairing: one QR, no server

The host's device generates:

```
sessionID  16 random bytes
sessionKey 32 random bytes   (never leaves the QR / the members' devices)
```

The QR encodes a single URL, already handled by the existing `circles-app:` scheme:

```
circles://buys/join?v=1&e=108&s=<sessionID b64url>&k=<sessionKey b64url>&h=<host pid>
```

Everything needed to join is *in the QR*, so pairing works with zero internet — scan and
you are in, whether you are on Bluetooth or on LTE. Derived, never transmitted:

- `bleTag    = HMAC(key, "ble")[0..2]`   — the 2-byte session tag in the BLE advertisement
- `relayTopic = HMAC(key, "topic")`      — the relay room name
- `aeadKey   = HKDF(key, "ops")`         — every op payload is sealed with ChaCha20-Poly1305

The relay therefore only ever sees an opaque room name and ciphertext. No circle.ms token,
no nickname, no item name ever reaches it. A human-readable code (`CIRCLES-4K7Q`) is shown
alongside the QR as a camera-failure fallback, resolved over the relay via SPAKE2 so the
short code is never enough on its own.

Anyone holding the QR is a full member. That is the intended trust model for a group of friends
at a booth. Removing someone is a **key rotation**, not a flag: the host generates a fresh
`sessionKey`, hands it to the remaining members over the existing sealed channel, and everything
derived from it — `roomId`, `contentKey`, `bleTag` — changes with it. A flag alone would leave the
removed device holding a key that still opens the old room. See §14.

## 5. Transports

One protocol runs over both links, so there is a single implementation:

```
HELLO  { sessionTag, deviceID, digest }
WANT   { versionVector }            // sent only if digests differ
OPS    { sealed op frames }         // chunked to the link MTU
```

### 5a. Bluetooth LE (the local path)

Bluetooth is what makes this work when the hall has no usable signal, and what keeps the
relay's reconnect cost down when it has a bad one. Every member is symmetric: peripheral (advertising + GATT server) *and* central (scanning).
Any two members converge, and a member who was out of range gets caught up by whoever they
meet first — an epidemic/gossip mesh, which is exactly right for a hall where the group
splits up and re-forms.

- One fixed 128-bit service UUID, identical on both platforms.
- Advertisement service data, 7 bytes, well inside the 31-byte legacy limit:
  `[2B sessionTag][4B digest][1B flags: member count, host bit]`
- Characteristics: `RX` (write-without-response, framed) and `TX` (notify).
- **The power rule**: a central connects *only* when a scanned advert's digest differs from
  its own, or when a peer has not been heard from in 10 minutes. In the steady state — the
  normal state, since the list changes a handful of times an hour — nobody connects at all.
- Android needs `BLUETOOTH_SCAN` with `usesPermissionFlags="neverForLocation"`,
  `BLUETOOTH_ADVERTISE`, `BLUETOOTH_CONNECT`. iOS needs the `bluetooth-central` and
  `bluetooth-peripheral` background modes.
- Known gap: iOS *background* advertising moves the service UUID into the overflow area,
  which only other iOS devices can see. A backgrounded iPhone can still scan and connect, so
  iOS→Android in the background falls through to the relay. Documented, not fought.

### 5b. Internet relay (the default path)

**Cloudflare Workers + Durable Objects, free plan.** The free tier's shape decides the design,
so the numbers matter:

| Free plan | Limit | What it means here |
| --- | --- | --- |
| Requests | 100,000 / day | One WebSocket **connection** = 1 request. Incoming messages bill at **20:1** (100 changes = 5 requests). **Outgoing messages are free**, as are protocol pings. |
| Duration | 13,000 GB-s / day | Billed only while JS executes — *provided hibernation is on*. |

Two consequences:

1. **Push, never poll.** Fan-out is free, so the relay pushes changes the instant they arrive.
   Polling would turn a free operation into a billed one.
2. **Hibernation is mandatory, not an optimisation.** A Durable Object holding a socket without
   hibernating bills duration the whole time — roughly 3,600 GB-s for one room over one 8-hour
   day. Four such rooms would exhaust the daily allowance. With the Hibernation API the object
   bills only while running code: milliseconds per change.

**The cost is connections, not traffic.** For 5,000 users making 20 changes each:

| Reconnect behaviour | Connections | Messages | Total vs 100,000 |
| --- | --- | --- | --- |
| One stable socket | 5,000 | 5,000 | **10,000** — comfortable |
| Drops every 30 min | 85,000 | 5,000 | **90,000** — at the edge |
| Drops every 5 min | 485,000 | 5,000 | **490,000** — 5× over |

So the engineering goes into *not reconnecting*: exponential backoff with jitter, no reconnect
while there is nothing to send and nothing expected, and letting Bluetooth carry the group while
the socket is down. The budget is **app-wide, not per-user**, and CiRCLES' traffic is spiky —
almost all of it lands in three days a year, so the peak day is what has to fit.

Rejected alternatives:

| Option | Cost | Verdict |
| --- | --- | --- |
| Firebase Realtime Database | Free tier caps at 100 concurrent connections | Rejected — that cap is exactly what breaks at a convention. |
| CloudKit public DB (already entitled) | Free | Rejected: iOS-only, would fork the code path. |

### 5c. When each is used

The relay is the default, because it reaches everyone regardless of where they are standing and
because fan-out over an already-open socket is free. Bluetooth is not a second-class fallback —
it does two jobs nothing else can:

```
socket up                    → relay carries it (cheap, reaches everyone)
socket down, peers in range  → Bluetooth carries it, and no reconnect is attempted
neither                      → hold locally, send when either returns
```

That middle line is what protects the request budget: on a flaky venue network Bluetooth absorbs
the churn instead of the client hammering out reconnects. It is also the only thing that works
when the hall has no usable signal at all — the situation that motivated this feature.

## 6. Talking to the relay

The relay is **already built**, in `../CirclesServer` (`circles-relay`), deployed to the Cloudflare
Workers free plan as `circles-relay-beta` (staging) and `circles-relay` (production). Its own README
is the authority on the protocol and limits. This plan covers the app side only.

What the client has to do:

### Connect

```
wss://<baseUrl>/r/<roomId>          roomId = 32 hex chars, from §4
```

One socket per session, opened when the session starts and held open. Reconnects use exponential
backoff with jitter, and are skipped entirely while Bluetooth is carrying the group — reconnect
churn is both the battery cost and the billing cost (§5b).

### Frames

`hello` must be the first frame; the reply is always an `ops` frame, empty when already current.

```jsonc
{ "t": "hello", "d": "<deviceId>", "v": { "<deviceId>": <seq> }, "k": "<relayAuthKey>",
  "ts": <unix seconds>, "a": "<tag>" }
{ "t": "ops", "o": [ { "d": "<deviceId>", "n": <seq>, "b": "<sealed>", "a": "<tag>" } ] }
{ "t": "bye" }
```

**Always send `k`, on every `hello`.** The server ignores it once a room has a key, and rooms are
deleted 48 hours after their last write — a client that sends `k` only once would be locked out of
its own room after an idle weekend. This costs 44 bytes and removes a whole failure mode.

Tags, with `deviceId` as its 8 ASCII hex characters and `blob` as the decoded bytes:

```
hello  = HMAC-SHA256(relayAuthKey, "hello" ‖ 0x00 ‖ deviceId ‖ 0x00 ‖ uint64be(ts))[0..16]
record = HMAC-SHA256(relayAuthKey, deviceId ‖ 0x00 ‖ uint64be(seq) ‖ blob)[0..16]
```

Verify the tags on records the server sends back, too — they are replayed unchanged, and the server
is not trusted (§8).

### Close codes

| Code | Meaning | What the client does |
| --- | --- | --- |
| `4001` | Rate limited | Back off hard; this indicates a client bug |
| `4002` | Bad frame or oversized | Log locally, do not retry the same frame |
| `4003` | Room full (8 sockets) | Fall back to Bluetooth; surface nothing |
| `4004` | Bad tag or stale `ts` | Not recoverable by retrying — the key is wrong. Fall back to Bluetooth; the list stays readable locally |
| `4005` | Room at 500 records | Stop sending; the session has outgrown a single shared list |
| `4006` | Room has no key (expired or never created) | Reconnect and send `hello` with `k`. Sending `k` every time makes this unreachable |

Every one of these is silent to the user (§11). None of them lose local data.

### Sending

- Coalesce per `syncRate` (§7), at most 32 records per frame, at most 4 KB per frame.
- Send only records the server is not known to hold, tracked from what it has echoed back.
- Never re-seal a record to re-send it (§8); send the stored bytes verbatim.

## 7. Configuration

Three facts have to reach both apps and be changeable without a release: **where the relay is**,
**whether the feature is on**, and **how hard to batch**. The two platforms get them differently,
because they have different free infrastructure already in hand.

| | iOS (CirclesApp) | Android (CirclesGo) |
| --- | --- | --- |
| `baseUrl` | CloudKit, fetched at runtime | Compiled in from a CI secret |
| `featureEnabled`, `syncRate` | CloudKit, same record | `relays.yml`, fetched from GitHub at runtime |

The asymmetry is deliberate. iOS already talks to a CloudKit public database for `RemoteConfig`, so
one more record type costs nothing and a single fetch gets everything. Android has no equivalent
free key-value store in the app, but it does have CI and a public repo — so the URL rides in as a
build secret, keeping it out of a public repository, and the switches ride in a public file that
can change without shipping a build.

Both platforms end up with the same three facts and the same failure behaviour.

### iOS — CloudKit

Container `iCloud.com.tsubuzaki.KamiSeries`, public database. New record type **`RelayConfig`**, one
record per feature, with `recordName` set to the feature ID so it can be fetched directly — no
query index needed, matching how `RemoteConfig` is read today.

| Field | Type | Example |
| --- | --- | --- |
| `featureId` | String | `sharedBuys` |
| `featureEnabled` | Int64 (0/1) | `1` |
| `baseUrl` | String | `https://circles-relay-beta.ktgk.workers.dev` |
| `syncRate` | Int64 | `0` |

Read it with `CKFetchRecordsOperation` and `desiredKeys`, the same shape as
`RemoteConfigProvider.fetchBroadcastMessage(timeout:)` in `App/Classes/RemoteConfig.swift` —
including reading the boolean back as `Int64`, which is what CloudKit returns for a checkbox and
what the existing `authEnabled` handling already assumes.

CloudKit's development and production environments give the debug/release split for free: the
development record holds the beta URL, production holds production.

### Android — GitHub

**The URL, at build time.** A `RELAYS_JSON` repository secret mapping feature ID to base URL:

```json
{ "sharedBuys": "https://circles-relay-beta.ktgk.workers.dev" }
```

`.github/workflows/deploy.yml` injects it exactly as `OPENID_JSON` is injected today, and
`app/build.gradle.kts` turns it into a `buildConfigField` in both `debug` and `release`, alongside
the existing `CIRCLEMS_AUTH_ENDPOINT` fields.

**The switches, at runtime.** `relays.yml` in the repository root, fetched from
`https://raw.githubusercontent.com/katagaki/CirclesGo/main/relays.yml`. It carries the feature ID
for mapping and, deliberately, no URLs — the file is public, the address is not.

```yaml
version: 1
features:
  - featureId: sharedBuys
    featureEnabled: true
    syncRate: 0
```

### `syncRate`

- `0` — send as soon as there is something to send, subject to the existing 400 ms coalescing
  window.
- `n > 0` — wait up to *n* seconds and batch whatever accumulates into one send. Best effort: a
  batch also goes early once it reaches the 32-record frame cap.

Worth being precise about what this buys. Raising `syncRate` cuts radio wake-ups, which is a real
battery win, and cuts inbound message count — which bills at 20:1 and is therefore already cheap.
**It does not reduce connections, and connections are the dominant cost** (§5b). The emergency
brake for the request budget is `featureEnabled: false`, not `syncRate`.

### Fetching, caching, and failure

- Fetch at session start, then at most every six hours. Short enough that a kill switch reaches the
  field the same day; long enough to cost nothing.
- Cache the last successful config and use it when a fetch fails.
- **No config and no cache → the relay stays off and Bluetooth carries the feature.** Fail closed on
  the network path, not on the feature. Identical on both platforms so behaviour cannot diverge.
- `featureEnabled: false` → never open a socket. The session still runs over Bluetooth, silently,
  per §11 — there is no error state to show.
- A config change never disturbs a running session's local state. It only decides whether the
  socket is opened.

### Worker hostnames

`circles-relay-beta.ktgk.workers.dev` for debug builds and the CloudKit development environment;
`circles-relay.ktgk.workers.dev` for release and production. Both are already deployed from
`../CirclesServer`, which tags `staging-*` to deploy the first and `v*` to deploy the second.

## 8. Security

### The invariant

**No transport is trusted.** Every change is sealed before it reaches either radio, and the exact
same sealed bytes travel over Bluetooth and over the relay. TLS and Bluetooth link encryption are
treated as bonuses on top, never as the thing protecting the data.

### Keys

`sessionKey` — 32 random bytes, generated by the host, exists only in the QR code and in members'
keychains. Everything else is derived from it with HKDF-SHA256 under distinct info strings:

| Derived | Info string | Used for | Who ends up holding it |
| --- | --- | --- | --- |
| `contentKey` | `circles-buys/v1/ops` | AES-256-GCM on every change | Members only |
| `roomId` | `circles-buys/v1/topic` | The relay room name | Members, Cloudflare |
| `bleTag` | `circles-buys/v1/ble/<window>` | 2-byte advertisement tag | Members, plus anyone in radio range |
| `relayAuthKey` | `circles-buys/v1/relay-auth` | The Worker's spam gate | Members, Cloudflare |

Derivation is one-way and domain-separated, so learning `roomId` or `bleTag` — both of which are
necessarily public — reveals nothing about `sessionKey` or `contentKey`.

### Cipher

**AES-256-GCM.** ChaCha20-Poly1305 would be the usual pick, but CirclesGo's `minSdk` is 26 and
Android's ChaCha20-Poly1305 needs 28; AES-GCM is present on both floors and hardware-accelerated
on both platforms. iOS uses CryptoKit `AES.GCM`, Android `javax.crypto` `AES/GCM/NoPadding`.

HKDF: CryptoKit provides it on iOS; API 26 does not, so Android gets ~20 lines of RFC 5869
extract-and-expand over `HmacSHA256`, checked against the RFC's own test vectors.

### Nonces — the one thing that must not go wrong

Every member encrypts under the *same* `contentKey`, so a repeated nonce would be catastrophic:
GCM leaks the XOR of the plaintexts and, worse, its authentication key. Random nonces risk
birthday collisions across devices; per-device counters collide with each other.

So the nonce is the change's own identity:

```
nonce (12 bytes) = deviceID (4 bytes) ‖ lamport counter (8 bytes)
```

`(deviceID, lamport)` is already globally unique — it is what makes a change *that* change — so a
nonce cannot repeat unless a device reuses its own counter. Three rules enforce it: seal once at
creation, store the sealed bytes, forward them verbatim. **Never re-seal an existing change.**

Associated data is `sessionID ‖ deviceID ‖ lamport ‖ kind`, so a sealed change cannot be moved
into another list or re-attributed to someone else without the tag failing.

### Who counts as a member

A change that decrypts and authenticates under `contentKey` was produced by someone holding
`sessionKey`. **That is the membership proof, and it is the only one clients trust.**

`relayAuthKey` is deliberately *not* that proof: the Worker holds it, so the Worker could forge
those tags. It exists only so the Worker can drop writes from strangers who somehow found a room.
Clients ignore it entirely.

Accepted limit: a shared symmetric key means any member could forge a change attributed to
another member. For friends splitting a shopping list, fine. If it ever stops being fine, the
upgrade is per-device Ed25519 keys exchanged in the `memberJoined` change.

Replay needs no separate defence — changes are idempotent and identified by
`(deviceID, lamport)`, so re-delivering one is a no-op.

### In transit: the relay

- `wss://` — TLS 1.3 to Cloudflare's edge, but nothing depends on it. Cloudflare itself, a
  corporate MITM proxy, or a mis-issued certificate all see only sealed bytes.
- No certificate pinning: Cloudflare rotates certificates, and pinning would buy nothing that the
  payload sealing does not already provide. ATS and `network-security-config` defaults apply.

### In transit: Bluetooth

- **Bluetooth's own link encryption is deliberately not used.** It requires pairing or bonding,
  and a system pairing prompt is exactly the friction a QR flow exists to remove. It is
  inconsistent across Android OEMs, "Just Works" pairing is MITM-able anyway, and none of it helps
  against a peer that connected legitimately. The link is treated as plaintext and the AEAD does
  the work — which is also why the Bluetooth and relay paths can share one implementation.
- The advertisement is public by nature: a 2-byte tag and a 4-byte state fingerprint. **No
  personal data is ever advertised.** To stop it becoming a tracking beacon, the tag rotates —
  `HMAC(sessionKey, "ble" ‖ floor(unixTime / 900))` changes every 15 minutes, and peers accept the
  previous, current and next window to tolerate clock skew. Platform MAC randomisation covers the
  rest.
- Any nearby device can connect to the GATT server and write to it. Defences: cap the frame size,
  rate-limit per connection, and drop the connection if the first frame fails to authenticate. An
  attacker can waste a little of someone's battery; they cannot read or inject anything.

### At rest

- `sessionKey` lives in the iOS Keychain as `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` — not
  synced to iCloud, not captured in backups — and in the Android Keystore. It is deleted when the
  session ends.
- Sealed changes sit in the existing app-group database. Item photos never leave the device
  unsealed.

### The QR code is the weak point, by design

- Anyone who photographs it becomes a member. That is the same trust model as handing someone
  your shopping list, and it is the price of pairing with no server and no accounts.
- Prefer the in-app scanner over the system camera: on Android a custom scheme can be claimed by
  another app, which would hand that app the key. Verified App Links and Universal Links for the
  paths that must go through the OS.
- Never log the join URL, and strip it from crash and analytics payloads.

### What is not protected

- **Traffic analysis.** The relay sees room IDs, message sizes, timing and IP addresses — enough
  to infer that a group of roughly N people is active, never what they are buying.
- **Presence.** Someone scanning Bluetooth nearby can tell that a CiRCLES session is running in
  the vicinity. Not whose, not what.
- **A member.** Anyone in the list can screenshot it. No design fixes that.

## 9. Power budget

- **Advertising** at a 1 s interval with a 7-byte payload costs on the order of hundredths of
  a milliamp — free, in practice.
- **Scanning** is duty-cycled: 2 s window every 30 s with the Buys list open, every 120 s in
  the background, backing off to 300 s after ten consecutive digest matches. The scan filter is
  a service-UUID filter, which both platforms push into the controller, so the application
  processor stays asleep through the crowd.
- **Connections happen only on a digest mismatch.** The prototype counts these avoided
  wake-ups ("syncs skipped by digest") to make the effect visible.
- **Coalescing**: local ops are buffered 400 ms before a flush, so rapid tapping through a
  list is one transfer, not eight.
- **One long-lived relay socket**, opened when the session starts and kept open. Keepalive is a
  protocol ping (free, per §5b) at 240 s rather than the 30–60 s a chat app would use.
  Reconnects use exponential backoff with jitter, and are skipped entirely while Bluetooth is
  carrying the group — reconnect churn is both the battery cost and the billing cost.
- **Deltas only.** The prototype's cold catch-up of a 9-op list was **1,035 B** over JSON
  (~400 B once CBOR-encoded). Steady state is **0 B** — the digest short-circuits it.
- **Images never travel over BLE.** A photo attached to an item syncs as a 32-byte content
  hash; the bytes are fetched on demand, and only over the relay or Wi-Fi.

## 10. Live Activity / Live Update

Starting a session starts the activity; ending it ends the activity. That is what keeps this
from being an always-on feature.

- **iOS**: ActivityKit. Lock screen shows the next unbought item assigned to you, its circle
  and space, group progress, and member avatars. Dynamic Island compact shows `3/7`. While
  the app runs, the sync engine updates the activity directly. While suspended, the
  Cloudflare Worker pushes to the ActivityKit push token over APNs — APNs is free and the
  entitlement (`aps-environment`) already exists.
- **Android**: a foreground service with an ongoing notification, upgraded to Android 16's
  `ProgressStyle` Live Update where available. FCM is free for the suspended case.

## 11. UI, reorganising what already exists

The app is map-first: a `NavigationStack` over `MapView`, with `UnifiedPanel` presented as a
sheet on iPhone and a docked panel on iPad, and `UnifiedViewPicker` (サークル / お気に入り /
宝物) in the panel's principal toolbar slot. There is no tab bar, and this feature does not
introduce one. Everything below lives inside the existing `.buys` segment.

**The UI never mentions the transport.** Bluetooth, the relay, version vectors, digests, queue
depths — none of it appears anywhere the user can see. Which radio carried a change is the
sync engine's business, and surfacing it would only ask the user to reason about something
they cannot act on. The one exception is a plain-language footer,
「まだ全員に届いていない変更があります。」, shown only while something genuinely has not
reached the group. Everything technical in the prototype lives behind the HARNESS chrome and
ships nowhere.

- **`BuysView`** keeps its structure — sections per circle, `BuysEntrySection` headers with
  `CircleBlockPill`, the day filter, the totals section, the existing `infoButton`. It gains:
  - a **「Justinと共有中」row** at the top: member avatars, who you are sharing with, a
    disclosure chevron. Tapping it opens the shared-list sheet. It is the only new element in
    the list, and it says nothing about how the sharing happens.
  - an **「共有する頒布品を追加」row** at the foot of the list — a plain row, matching how the
    rest of the app adds things, not a floating button.
  - an **「あなたの分」row** above the existing 合計 / 総合計 rows.
- **Shared-list sheet** (new): the pairing QR under a line saying that scanning it joins the shared list, a short code beneath that, the member list as
  plain names and avatars, and 「この端末で共有を終了」. Four things, no status readouts. When
  no session is running the 宝物 segment instead offers 「共有リストに参加」/「共有リストを作成」.
- **`BuyItemRow`** keeps its tap-to-cycle status behaviour exactly as it is today
  (pending → bought → cancelled); the tap now also emits a `setStatus` op. It gains a trailing
  **assignee avatar** (tap → assign sheet), a tinted row background when the item is yours,
  and a 「%@が購入しました」subtitle when someone else moved it.
- **Unchanged**: the day filter, circle-detail navigation, the image viewer, `UnifiedPanel`
  detents, and the iPad docked-panel layout.

Strings follow the app's existing vocabulary — 宝物 for Buys, 頒布品 for items, 値段 for cost —
and are localized in `Localizable.xcstrings` (ja + en), mirroring `values/strings.xml` and
`values-ja/strings.xml` on Android.

The shared list is a *second* list, not a replacement. A private item can be promoted into the
shared list, which emits an `addItem`.

## 12. Storage

Reuse the existing per-event SQLite in the app group (`AXiS/BuysDatabase.swift`), adding:

```sql
CREATE TABLE SharedSessions (sessionID TEXT PRIMARY KEY, key BLOB, eventNumber INT,
                             hostPID INT, startedAt INT, endedAt INT);
CREATE TABLE SharedOps (opID TEXT PRIMARY KEY, sessionID TEXT, lamport INT, device TEXT,
                        actor INT, kind INT, itemID TEXT, circleID INT, text TEXT, value INT);
CREATE TABLE SharedPeers (sessionID TEXT, deviceID TEXT, vector TEXT, lastSeen INT);
```

`sessionKey` goes in the keychain / Android Keystore, not in the table. The op log is
compacted to a snapshot when a session ends. Private `BuyEntries`/`BuyItems` are untouched.

Golden op-log vectors land in step 1 and gate every later step on both platforms.

## 14. Known problems, and what is being done about them

### A backgrounded iPhone is invisible to Android — **closed**

iOS moves the service UUID into the advertisement's overflow area when the app is not in the
foreground, and only other iOS devices scanning for that UUID can read it. This was a real hole
when Bluetooth was the primary path.

**Decision: Android is the advertiser of record.** CirclesGo already runs a foreground service for
its Live Update, so it can advertise reliably for the whole session. That closes the matrix:

| | Android peer | iOS peer, foreground | iOS peer, background |
| --- | --- | --- | --- |
| **Android** | normal advertise + scan | sees iOS advert | scans, finds Android's advert |
| **iOS, background** | scans, connects outward | scans, connects outward | overflow area, visible iOS-to-iOS |

The residual cost is latency, not connectivity: background scanning on iOS is throttled, so a
Bluetooth-only catch-up may take tens of seconds. The relay covers the fast path, so that is
acceptable.

### Bluetooth congestion in a hall of tens of thousands — **mitigated by design**

Discovery itself is cheap: the scan filter is a service-UUID filter that both platforms push into
the controller, so the application processor sleeps through the crowd. Connection *setup* is what
degrades in dense RF.

**Decision: the design already avoids most connections** — a peer whose advertised fingerprint
matches ours is never connected to at all. On top of that: at most two concurrent connection
attempts, one attempt per peer per 60 s after a failure, give up on a peer until its fingerprint
changes, and never block the UI on a transfer.

### Anyone who photographs the QR is a member — **narrowed**

Instant joining is the point, so a host-approval prompt is not the answer.

**Decision: make it visible, and make removal real.** Every member sees 「Aoiが参加しました」when
someone joins, and the member list is one tap away — an uninvited join is noticed. More
importantly, **removing a member rotates the session key**: a new `sessionKey` is generated and
handed to the remaining members over the existing sealed channel, which changes `roomId`,
`contentKey` and `bleTag` together. The removed device keeps only bytes it can no longer decrypt
and a room nobody is using. A revocation flag alone would not have done this — the old key would
still open the old room.

### If the free allowance runs out, it runs out for everyone at once — **accepted, with guards**

There is no second relay now. The failure is app-wide and lands on the three days a year that
matter.

**Decision: guard the input, not the output.** Reconnect churn is the only thing that can realistically
exhaust the budget (§5b), so the client-side reconnect discipline *is* the mitigation. Alert at
50% of the daily cap in Workers Analytics. If it is ever hit, Bluetooth and local queueing carry
the feature — degraded to line-of-sight, but working, and silent per §10.

### Clocks drift, and the Bluetooth tag depends on one — **bounded**

The rotating advertisement tag is derived from a 15-minute time window, so two phones with very
different clocks would compute different tags and never recognise each other.

**Decision: accept the neighbouring windows.** Each device matches the previous, current and next
window, so a phone whose clock is up to about 15 minutes out still pairs. Both platforms sync time
from the network by default, making a larger drift unlikely. Note this affects *discovery only* —
ordering never uses wall-clock time.

### iPad's docked panel is only 360pt wide — **designed**

`UnifiedPanel` docks to a 360pt sidebar on iPad, where the new rows are tightest.

**Decision:** the sharing row drops the names and shows avatars plus a count when width is
constrained; in item rows the name truncates while the cost and the assignee avatar stay pinned
right. The shared-list sheet is presented as a **sheet, not a popover**, with an oversized QR —
an iPad is held further from the phone scanning it, so the code needs to be physically larger,
which a popover cannot give.

### Still open

- Whether the Worker's outbound APNs/FCM calls count against the free request allowance. They are
  subrequests rather than inbound requests, which suggests not, but this needs confirming before
  step 4 — it changes the budget maths if it does.

## 15. Where this stands

Implemented on branch `claude/better-buys` in both app repos. The relay is on `main` in
`../CirclesServer`.

On iOS the sync layer lives in its own framework, **ORBiT**, joining `AXiS` (database) and
`RADiUS` (API) — the model, crypto, relay client, Bluetooth transport and Live Activity
attributes. Views stay in the app target, and the widget extension links ORBiT for the
activity attributes.

### Built and verified

- Change log, fold and version vectors — the **ORBiT** framework (iOS), `sharedbuys/` (Android).
- Key derivation, AES-256-GCM sealing and HMAC tags. **Three independent implementations agree**:
  Swift, Kotlin, and a Node peer written as a test oracle. All three derive the same room ID from a
  key and open each other's records.
- Relay client on both platforms, against a locally run `wrangler dev`.
- **Cross-platform convergence** — iOS and Android joined to one room, each adding items, both
  ending at the same list.
- Reconnect with exponential backoff and jitter, suppressed while Bluetooth peers are present (§5c).
- Bluetooth transport: rolling-tag advertisement carrying the state digest, GATT inbox/outbox,
  chunked framing, and the digest short-circuit that avoids connecting to a peer already in sync.
- Live Activity: lock screen and Dynamic Island, re-adopted after an app restart, updating on every
  change.

### Not verified

- **Bluetooth convergence over a real radio.** Neither the simulator nor the emulator has one; this
  needs two physical devices. The parts that must match across platforms are covered by a self-test
  that produces identical output on both — digest `cb8909f9` for the same version vector, and a
  500-byte payload chunking to 4 frames and reassembling out of order. Everything above the radio
  is the same code the relay path uses, which is verified.
- ActivityKit push updates (§10) — needs a device and the Worker's push path.

### Deliberate shortcuts, to revisit

- **Storage is a JSON file** in the app group (iOS) and SharedPreferences (Android), not the SQLite
  tables in §12. Fine for hundreds of changes; replace before the log grows or compaction matters.
- **Config is not wired up.** §7's CloudKit `RelayConfig` and Android's `RELAYS_JSON` + `relays.yml`
  are unimplemented; the relay URL is a field in the debug harness instead.
- **The shared list is not in `BuysView` yet.** It exists only behind the debug harness — none of
  the UI work in §11 has been done.
- `syncRate` batching is not implemented; changes send immediately.
- Photos, member removal with key rotation, and the short pairing code are not implemented.

### The debug harness

Both apps expose the same URL scheme. Nothing here ships; it is how the feature is driven without
the real UI.

| URL | Effect |
| --- | --- |
| `circles-app://buys-debug` | Open the harness screen |
| `circles-app://buys-join?v=1&e=0&k=<key>` | Join a session from a base64url key |
| `circles-app://buys-add?name=…&cost=…` | Add an item |
| `circles-app://buys-cycle?item=<id>` | Cycle an item's status |
| `circles-app://buys-selftest` | Print the digest and framing check to the log |

Run against a local relay only:

```
cd ../CirclesServer && npx wrangler dev --port 8787 --local
```

The iOS simulator uses `ws://127.0.0.1:8787`; the Android emulator uses `ws://10.0.2.2:8787`, with
a debug-only network security config permitting cleartext to those hosts. Release builds are
`wss://` only. **Do not point the harness at the deployed Workers** — the free-tier request budget
is shared with everyone (§5b).
